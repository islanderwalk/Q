文字雲斷詞 Pipeline 重建

題目列了五個症狀，根因只有三類：斷詞前沒清洗、沒有停用詞過濾、字典缺詞又和搜尋端不一致。這份研究把答案拆成回朔策略、字典維護、版本一致性三塊，關鍵假設都用 jieba 在 41.8 萬筆 PTT 語料上實測過。

  • 估算要先列假設，並把機器時間和人力時間分開。

加一個新詞，會影響哪些文章？

jieba 對每個候選切法打分：每個詞 log(詞頻) − log(total) 加總，取最大。add_word 會把新詞頻率加進 total（原始碼第 428–429 行），覆寫舊詞時也不會扣回舊頻率。所以不含新詞的句子，候選切法雖然不變，分數卻全部平移；原本平手的切法可能翻轉，平移大時還會偏向切出較少的詞。

情境（取樣 200,000 篇）total含新詞且改變不含新詞卻改變
不含新詞卻改變的例子之前之後

預設累加時，小幅改變多半是平手翻轉（同一組詞換了順序，例如「咕咕／咕」），對詞頻統計沒有影響；給極端頻率時則是少切一刀（「他／國」→「他國」）。把 total 固定成字典版本裡的常數之後，三種情境都是 0：不含變更字串的句子在數學上不會變，影響範圍就能用「原文含這個字串」精確圈出。

(b) 字典維護與共用

字典當程式碼管理；核心詞庫共用，用途層、斷詞粒度、生效時間各自控制。

維護流程

  1. 候選來源

    搜尋 log 每週前 1,000 名（不在字典或會被切開者）、客戶監測關鍵字、地名庫（行政區、商圈、夜市、捷運站）、品牌與公司名、新詞發現、PM 與客戶回報。

  2. 新詞發現

    每週對新資料算 n-gram 頻率 + 凝固度（PMI）+ 左右鄰字熵，找「常一起出現、邊界又很自由」的字串；再加上 CKIP 斷成一個詞、jieba 卻切開的差集。

  3. 人工審核

    候選清單附出現次數、例句、預估影響篇數；分析師或 PM 每週核可，不自動上線。

  4. PR 進 Git

    每個詞記錄頻率、詞性、類別、來源、新增者、日期。改字典和改程式一樣走 code review。

  5. CI

    格式檢查（重複、衝突、含標點、單字詞）；回歸測試（必不可拆清單 100%、五個症狀偵測器 = 0、golden set 差異報告）；用 BigQuery 掃原文估影響篇數。

  6. 每週發版

    產出 jieba 字典（含固定 total）、搜尋端字典與同義詞、停用詞、變體表，放 GCS 並附 checksum。串流重新載入新版；批次只重跑受影響文件；搜尋端依自己的節奏。

斷詞用字典 vs 搜尋用字典：共用還是分開？

共用核心詞庫（建議）各自一份字典
維護一條流程、一套 CI兩條流程，還要同步工作與每日差異報表
症狀 5（搜尋熱詞不在文字雲）結構上就一致靠同步維持；一不同步就復發
點文字雲的詞往下查詞可以直接當查詢，計數對得上要有「詞 → 查詢」轉換層，數字可能對不上
版本一個 dict_version，兩端各自釘版兩組版本標記，兩組回歸測試
工期（原團隊估）約 10 天再多 20 天以上
代價一次改動影響兩端，要用版本釘選分開生效時間長期一定會漂移

共用字典不等於共用粒度。搜尋要召回，用細粒度（jieba 搜尋模式、IK 的 ik_max_word）；文字雲要可讀，用精確模式。實測：同一份字典，「台北捷運週末加開班次」精確模式切成 台北捷運/週末/加開班次，搜尋模式切成 台北/捷運/台北捷運/週末/加開/開班/班次/加開班次。

共用來源，不共用生效時間。文字雲每週發版，只重跑受影響文件；搜尋端的同義詞放在 search analyzer，可用 _reload_search_analyzers 重新載入（只支援 search analyzer 裡 updateable 的 synonym filter）官方文件。index-time 斷詞的變更累積到排定的 reindex：IK 這類詞典熱更新只會影響之後寫入的文件，舊文件的倒排索引是寫入當下產生的 推論。

如果走不同字典，架構上會多出：兩份字典的同步與差異報表；下鑽用的「詞 → 查詢」轉換層；ES 端兩組 analyzer 與版本標記；兩套回歸測試與發版節奏。原團隊估的多 20 天，花在這些同步與對帳，寫字典本身反而不是大頭。

(c) 串流與回朔一致、字典更新可控

原則：斷詞 = f(原文, seg_ver)。同一份原文、同一個版本，不論批次或串流，結果必須一模一樣。

讓結果只取決於版本

  1. 同一個映像、同一個字典版本

    批次（Cloud Run Jobs）和串流（Cloud Run 服務）跑同一個 segmenter 映像，從 GCS 載入同一個字典版本並驗 checksum。

  2. 不在常駐 process 裡熱改字典

    jieba 的 add_word 每次都改 total，覆寫舊詞不扣回舊頻率，del_word 還會改到整個 process 共用的強制切分集合。換版就整份重新載入，並把 total 固定成字典版本的常數。

  3. 每篇記 seg_ver，版本只能前進

    寫入用條件更新：新版本大於等於既有版本才寫，避免慢的回補 job 用舊版蓋掉串流剛寫的新版。

  4. 每天影子比對

    從串流抽 1 萬篇，用批次路徑以同版本重算，差異必須是 0。這是不變量，不是「越少越好」。

載入方式（Python）
tk = jieba.Tokenizer(dictionary=artifact.path)  # 每次整份載入
tk.initialize()
tk.total = artifact.total  # 固定正規化常數
# 不要在常駐 worker 裡 add_word / del_word 熱更新

POST posts-2024.05/_update/<doc_id>

演算法層換斷詞器或模型、改過濾邏輯、改 total全量全部開 terms_v3，照 (a) 的批次流程跑，藍綠切換

「只重跑受影響文件」的前提是 total 固定：實測不固定時，加 1 個詞就有 52 篇不含該詞的貼文改變；固定後是 0（見「實測」頁）。流行語的影響範圍可能很大：實測 6 個 PTT 流行詞影響 5% 的貼文，發版前要先估篇數，超過門檻（例如 2%）就排夜間限速。

發版時序與收斂條件

  1. T0 發版

    CI 全過，新版字典放上 GCS；manifest 記下變更詞與預估影響篇數。

  2. 串流換版

    串流 worker 滾動重啟、載入新版；之後的新文章都是新 seg_ver。

  3. 圈出受影響文件

    BigQuery 掃原文，找出含任一變更字串、且 seg_ver 小於新版的 doc_id。

  4. 限速重跑

    同一個批次 job 以 doc_id 清單執行，條件寫入。

  5. 收斂檢查

    「含變更字串且 seg_ver < 新版」的篇數 = 0 才算發版完成；抽樣不含變更字串的文件重算，差異 = 0。

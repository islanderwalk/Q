## 搜尋為什麼一度變慢（`restart-`）

同一個「颱風」查詢，在搜尋頁上的耗時是：

| 組 | 拍攝時間 | 耗時 |
|---|---|---:|
| `backfill-` | 01:22 | 2,200 ms |
| （無前綴） | 02:56 | 12,891 ms |
| `drill-` | 02:58 | 18,399 ms |
| `restart-` | 03:15 | 1,466 ms |
| `reconnect-` | 07:10 | 10,125 ms |

03:12 重啟 BigQuery 模擬器之前與之後各量一次：

| | 模擬器記憶體 | CLI 查詢 3 次（query_ms） | `/api/search` 3 次 |
|---|---:|---|---|
| 重啟前（03:11） | 1,022 MiB | 6,625／6,654／7,654 | 11.5／6.9／6.2 秒 |
| 重啟後（03:13） | 112 MiB | 2,870／1,672／1,401 | 1.5／1.6／1.4 秒 |

重啟前後，模擬器裡列得出來的查詢工作紀錄都是 0 筆（程式每查完一次就刪掉，crawler 啟動時也會清一次），所以不是殘留的工作拖慢。變慢的時候模擬器記憶體是 1,022 MiB，重啟後降到 112 MiB。模擬器的 SQL 解析器跑在 WASM 裡，要等 Go 的 GC 才會釋放記憶體（見 [`pipeline/README.md` 的「為了 BigQuery 模擬器做的調整」](../../pipeline/README.md#為了-bigquery-模擬器做的調整)）。重啟之後就回到 README 寫的 1–3 秒。資料存在 volume 裡，重啟不會掉。這是模擬器才有的現象，GCP 上的 BigQuery 不用重啟。

重啟 4 小時後（07:10 拍 `reconnect-`），搜尋頁又是 10,125 ms。07:34 沒有重啟，用同樣的方法再量一次：

| | 模擬器記憶體 | CLI 查詢 3 次（query_ms） | `/api/search` 3 次（回報的 took_ms） |
|---|---:|---|---|
| 07:34（重啟後 4 小時 20 分） | 841 MiB | 5,213／1,001／1,154 | 1,294／985／1,008 |

只有第一次慢，後兩次都在 1 秒左右；03:11 那次是三次都要 6–8 秒。所以 07:10 不是又回到重啟前那種狀態。比較可能的原因有兩個：

- 隔一陣子沒查之後，第一次查詢本來就比較慢（03:13 重啟後也是第一次最慢）。
- 截圖程式拍完二十多張看板才開搜尋頁，電腦當時比較忙：07:10–07:11 之間，同一台電腦上的 Q6 採集器有三個來源都 30 秒逾時。這一點沒有直接證據。

記憶體長到 841 MiB，後兩次查詢仍在 1 秒左右。「記憶體一長就變慢」目前只在 03:11 看到一次，要不要定期重啟模擬器，還要再觀察。

## 看圖時要知道的事

- 搜尋頁一次只列出前 50 篇，命中總數以 CLI 或 API 為準。
- 「② 事後刪文 404」是 1 小時視窗的加總。刪文如果發生在視窗外，圖上就是 0。
- 「① 單次請求失敗」（[`panel-27.png`](panel-27.png)）大約每小時有 1 次 error，「PTT 回應時間」（[`panel-14.png`](panel-14.png)）的 p95 也常在每輪開頭到 20 秒。兩個都是因為每輪第一個請求（讀最新列表頁）沿用了上一輪留下的連線：
  - 11-03 21:05 到 11-04 03:05 的 7 個整點輪次，每輪剛好有 1 次 list 的 error。
  - 閒置 44–58 分鐘的 5 輪，各有 1 個列表頁請求等滿 20 秒逾時。
  - 閒置 7 和 14 分鐘的 2 輪，error 在幾秒內就回來。
  - 容器剛啟動、第一個請求用新連線的 8 輪，都沒有 error。
  - 失敗後重試一次就讀到，不影響入庫。

  「PTT 回應時間」在兩輪之間沒有資料點，看板把前後兩點直接連起來，所以 p95 看起來像花了一小時爬到 20 秒。程式已經改成閒置超過 60 秒的連線不再沿用；前四組截圖都是改之前拍的，改之後見下一節。每一輪的數字在 `run_summary.json` 的 `request_errors_12h`。
- 回補那組（[`backfill-dashboard-full.png`](backfill-dashboard-full.png)）在 11-03 16:21 到 17:57 左右（看板上是 00:21 到 01:57）有一段請求一直失敗：「① 單次請求失敗」堆到 14，「退避等待」一直是 5 分鐘，「每分鐘請求數」幾乎是 0。這段的請求大多花 10–20 秒，都沒有拿到 HTTP 狀態碼（記成 error，不是 5xx）。連續失敗 3 次之後，每次都先暫停 5 分鐘再試，1.6 小時之後恢復。7 篇抓取失敗就是這一段，下一輪已經補抓。當時的容器後來重建過，log 沒有留下，查不到是哪一種錯誤。現在每一次失敗（包括重試成功的那幾次）都會把種類記進 log。

| 04:05 | 29 分 12 秒 | ok，新文 43 篇，104.5 秒 | 4 次，都是 200、都在 10 秒內 | 無 |

- [`reconnect-panel-27.png`](reconnect-panel-27.png)「① 單次請求失敗」：橘色的 error 最後一段來自看板上 11:05 那輪（03:05，換版前）。之後只有 13:05 起一小時寬的藍色，是 05:05 那輪的 525（1 小時視窗，所以畫成一小時寬）。525 是 Cloudflare 回的，表示它跟 PTT 主機之間的 TLS 交握失敗，不是我們這邊的連線。03:34 那次 525 圖上沒有：狀態碼只有 error 預先建成 0，525 第一次出現時序列從 1 開始，`increase()` 看不到這一步，log 裡有記。
- [`reconnect-panel-14.png`](reconnect-panel-14.png)「PTT 回應時間」：最後一次到 20 秒是看板上 10:05（02:05 那輪）。換版後每輪開頭的 p95 都在 1 秒以內。

流程八步

完整版在 b-c-d.md
  1. 盤點：抽樣掃 GCS 歷史 JSON 的所有 key 組合，建別名表；quality.json 列出每個分區的 key 與次數。
  2. Mapping：update mapping 在現有 index 加欄位與 counts_at.<欄位>，加新欄位不需 reindex。
  3. 切批：平台 × 週，每批獨立 bulk 檔（500 篇、5 MB 上限），附 sha256。
  4. 合併：同一篇多次抓取，每欄取「有值」的最新一次；null 算有值，缺 key 算不知道。
  5. 寫入：bulk update＋painless 腳本，逐欄比 counts_at，較舊就不動；一欄都沒寫就是 noop。
  6. 限速：每秒請求數上限、離峰；429／5xx 隨機指數退避，只重送被拒的筆。不改線上 refresh_interval。
  7. 核對：壞行 >1%、整檔壞、任一分區某欄不知道 >20% 就停（退出碼 3）；送出後抽 1% 讀回比對。
  8. 續跑：送完一檔記進 sent.json，中斷後只送沒送完的檔。

另一條路是建新 index＋reindex＋alias 切換：要整份複製、暫時兩倍空間，只有既有欄位要改型別時才划算。

需求點名的三個風險

風險對策
歷史欄位名不一致盤點後補別名表、統計每個舊名用了幾次；同一筆兩個名稱值不同記 alias_conflict 不寫入。別名表沒有的新名稱會被分區關卡擋下（上面那張表）。
原始資料缺漏某次抓取少了 key 記為不知道，不蓋掉其他次的值；全部都缺就不寫，前端顯示「—」，不補 0。只接受 JSON 整數，「萬」字串當不知道。

(d)SLA：瓶頸在抓取頻率，不在寫入

設計摘要

首次可見延遲模擬

貼文在兩次輪詢間隨機發布 → 等下一次抓取 ＋ 寫入鏈路
—P95 延遲
—最壞情況
—1 小時內可見
—告警狀態

模型：發布時間在輪詢間隔內均勻分布，延遲＝距下次抓取的時間＋寫入鏈路。所以 P95 ≈ 0.95 × 間隔＋鏈路，最壞＝間隔＋鏈路。限速造成的 Pub/Sub 積壓會直接加在鏈路上。

指標計算告警
首次可見延遲ES 寫入時間 − published_at（每篇記在文件裡）P95 > 45 分 警告 P95 > 60 分 呼叫
首次抓取達成率1 小時內被抓到的新文章 ÷ 新文章總數< 95%

名詞這頁用到的詞

關鍵路徑／關鍵鏈
從開工到上線最長的一串先後工作；上面任何一件延誤，上線就延誤。這題把「同一人手上的下一件」也算成先後關係。
總浮時
一件工作最多能晚多久完成，而不延後整個專案。
API 契約
先講好 API 的欄位名與格式；FE 拿到契約就能用假資料開工，不必等 BE 做完。
counts_at
每個計數欄位各自的抓取時間（epoch 毫秒）。回補腳本拿它判斷誰比較新。
painless／noop
painless 是 ES 內建的腳本語言；腳本判斷不用寫時回 noop，文件完全不動。
refresh_interval
ES 多久把新寫入變成可查詢。大量匯入時常調大或關掉，但在線上 index 這樣做，新貼文就查不到。
alias
指向某個 index 的別名；建新 index 後切 alias，查詢端不用改名。
play_count／video_view_count
需求寫 video_view_count，實抓 IG Reels 只看到 play_count；兩者是否同一定義要和 PM 確認。
quote_count
Threads 的引用數。畫面上的「轉發」＝轉發（repost）＋引用（quote）。
金絲雀帳號
固定幾個會定期發文的帳號，用來端到端驗證新貼文是否準時出現。

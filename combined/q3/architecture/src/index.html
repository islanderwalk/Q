PTT 全文搜尋：八卦板 7 天全文搜尋 ETL

我想做一個 PTT 八卦板全文搜尋：使用者輸入關鍵字，查出過去 7 天內所有包含該關鍵字的文章，以及文章下的留言。要設計能滿足這個需求的 ETL Pipeline。

資料規格：

  • 文章即時性：新文章需在發布後 6 小時內納入搜尋範圍。
  • 留言新鮮度：包含關鍵字的文章，其留言在 7 天內每天至少更新一次。

工程約束：

  • 我一個人維運，目標兩週內上線。
  • 技術棧用 GCP + Python。導入棧外的東西需要額外說明理由。
  • PTT 是別人的網站，沒有 API，過度請求會被擋。

遇到的瓶頸：

  1. 每天要打 PTT 多少次？先估規模（文章數／留言數／文字量／每日抓取請求數），再開始設計。你的架構必須和你的估算數字一致。
  2. 每個環節用什麼 infra、理由是什麼？架構圖要寫清楚，不寫程式碼，pseudo code 就夠。
  3. 上述兩條資料規格，哪一條主導成本？ 兩者相差多少倍？
  4. 我怎麼確認抓到的資料沒有遺漏？需要一個可以自動檢查的不變量（invariant），而不只是「比對筆數」。
  5. 哪三件事不監控？各自的風險為什麼可以接受？
  6. 若某項規格不合理或定義不清，要不要修改？修改要說明代價。

排程

Cloud Scheduler：每小時觸發一次

ETL 主體（Extract → Transform → Load）

Cloud Run Job「crawl」

Python｜單一 worker 依序抓｜每秒 1 次｜每小時跑約 5–8 分鐘

規格 1 ① discover：找新文章並首抓

從上次的頁碼重讀到最新頁（跳過置底公告），新文章各抓一次 → 發文後 1 小時內入庫

≈ 938 次/天
規格 2 ② refresh：重抓 7 天內的文章

挑「發文 7 天內、且 23 小時以上沒抓過」的文章重抓留言 → 每篇每天更新一次

≈ 5,340 次/天
③ 共用：抓取 → 解析 → 寫入

解析內文、留言、刪文佔位；失敗退避重試；狀態全存在 BigQuery，失敗下一輪自動補

原始資料

Cloud Storage：原始 HTML

gzip 壓縮、保留 30 天；7 天份約 105 MB
解析規則改了可以直接重新解析，不必重爬 PTT

整理後的資料（依發文日分區）

BigQuery

  • articles：文章 ID、標題、作者、發文時間、內文、上次抓取時間（約 6,200 列）
  • comments：文章 ID、序號、推/噓/→、帳號、內容、時間（約 23 萬列）
  • index_slots：頁碼、格位、文章 ID（比對列表推文數用）
純文字約 23 MB 爬蟲狀態也存這裡 → job 可重跑不重複
查詢服務

Cloud Run Service「search」（FastAPI）

子字串比對、不需斷詞；只掃最近 7 天分區；每次查詢約 1–3 秒

使用者

輸入關鍵字 → 7 天內的文章與留言

資料品質（瓶頸 4）

Cloud Run Job「verify」：每天一次

  • 從最新頁沿「上頁」往回走，走到出現早於 7 天前的文章為止
  • 途中每一頁都讀取成功，走完時最新頁沒有變
  • 看到的每個未刪除文章 ID，都有一筆抓取成功（200）的文章

文字雲斷詞 Pipeline 重建

情境：一個社群輿情分析 SaaS 平台，主力產品是讓企業客戶輸入關鍵字後，即時查詢跨社群平台（Facebook、Instagram、YouTube、論壇、媒體、Threads）的聲量趨勢與文字雲。

目前的文字雲功能使用一份維護多年的繁體中文字典檔進行斷詞，但產出品質有嚴重問題：短網址後綴出現在結果中、電話號碼被當成詞彙、中文助詞（的、了、在）未被過濾、地名變體被拆散（例如「高雄市」被拆成「高」「雄」「市」）、搜尋高頻詞反而沒出現在文字雲中。

為什麼這樣切

切批策略五點

  • 可控規模一批平均約 185 萬篇，跑完和驗完都在掌握得住的範圍。
  • 問題隔離哪一批沒過，人修好後只重跑那一批，已通過的不受影響。
  • 業務驗收每個渠道的首批先給 PM 看 A/B，簽了才放同渠道其他批（首批被人工豁免也一樣要簽）。
  • 資源平衡G3 盯線上負載，超過門檻自動降速。
  • 可追溯每批的狀態、checkpoint、沒過原因都記在批次狀態紀錄（manifest）。
放大看 · 三層去重

同一篇文章怎麼只算一次：三層去重＋G1 對帳

同一篇文章可能被碰到兩次：原文檔裡重抓了一行、程式中斷後重跑、或兩個 task 撞在一起。沒擋住的話，同一篇可能被算兩次（G1 會對不上）、寫成兩份（搜尋會看到重複），或白做兩次工（G1 不一定看得出來）。回補用三道關卡擋掉。下面的資料都是示意；程式碼是 repo 裡實際在跑的程式，只為了好讀把縮排縮小，字沒改。

partition_id　分區編號

例：「ptt/2026-09」

代表一個渠道的一個月（一大包文章）。它管的是「這一包由誰做」。正常情況下，一個分區同一時間只會被一個 task 領走；只有心跳停太久、被別人接手時，才可能短暫兩個 task 重疊，那時靠第三層擋住（見下方「常見誤會」）。用在第一層。

post_id　文章編號

例：「Kaohsiung/M.1793281424.A.0CF」

代表一篇文章。同一篇不管被抓幾次，編號都一樣。它管的是「這一篇算過沒」。用在第二層、第三層。

最容易搞混的一點：partition_id 不是拿來去重文章的。它只管分工；真正認「是不是同一篇」的是 post_id。
